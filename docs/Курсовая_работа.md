## Аннотация

Разработано настольное приложение для просмотра каталога товаров и оформления локальных предзаказов. Каталог загружается через HTTP из DummyJSON Products API и сохраняется в SQLite; данные заказов обрабатываются и хранятся локально. Пользователь может искать товар, отбирать его по категории, сортировать каталог, просматривать подробности позиции, выбирать количество и оформлять либо отменять заказ в разрешённом состоянии. Цена позиции фиксируется при оформлении. Реализация разделена на доменную модель, слой хранения данных, интеграцию с API, сервисы бизнес-логики, ViewModel и Avalonia-представления.

## 1. Введение

### Актуальность

Предзаказ позволяет покупателю выразить намерение приобрести товар до его поступления. Для демонстрации такого сценария нужна система, которая разделяет источник товарного каталога и собственные заказы магазина. Без этого разделения изменение цены или повторная загрузка каталога может повредить сведения, уже сохранённые в заказе.

Учебный проект актуален как пример настольного приложения, объединяющего интерфейс, сетевой клиент, локальную реляционную базу и проверяемую бизнес-логику. Он показывает типичный сквозной сценарий: получение удалённых данных, их отображение, запись пользовательского действия и восстановление состояния после повторного запуска.

### Цель работы

Цель — разработать функциональное настольное приложение каталога предзаказов, которое получает демонстрационные товары через публичное API и надёжно сохраняет заказ пользователя в локальной базе SQLite.

### Задачи

Для достижения цели необходимо изучить сценарий предзаказа и ограничения тестового источника данных; сформулировать функциональные требования; спроектировать модель предметной области и реляционные связи; реализовать Avalonia-приложение на MVVM; изолировать сетевой источник через интерфейс; обеспечить идемпотентную синхронизацию; реализовать оформление и допустимую отмену заказа; проверить основные правила интеграционными тестами; подготовить руководство пользователя.

### Объект и предмет

Объектом исследования является процесс представления каталога и регистрации намерения клиента приобрести товар до ожидаемого поступления. Предметом — архитектура и программные средства настольной системы, сохраняющей товарные позиции и предзаказы в локальной БД при обновлении товарного каталога из внешнего API.

## 2. Анализ предметной области

Каталог и предзаказ имеют разные источники истины. Название, категория, описание, цена, картинка и поле `stock` поступают из демонстрационного API и могут измениться при повторном чтении. Сам факт заказа, выбранное количество, дата создания и цена, по которой пользователь оформил заказ, создаются приложением и должны сохраняться независимо от внешнего каталога.

DummyJSON Products предоставляет демонстрационные карточки и операции чтения списка, поиска, категорий, фильтрации и сортировки. Документация предупреждает, что добавление, обновление и удаление имитируются: изменения не сохраняются на сервере. API не предоставляет сущности предзаказа, подтверждение заказа и календарь будущей поставки [1]. Поэтому проект не выдаёт тестовый источник за реальный магазин. Ожидаемая дата поступления генерируется локально для демонстрации поля, а статус заказа существует только в SQLite.

Главные пользовательские сценарии: загрузить товары при пустой локальной базе; открыть сохранённый каталог при последующем запуске; синхронизировать позиции; найти товар и выбрать его; проверить доступность и количество; создать предзаказ с фиксацией цены; найти его в истории; отменить заказ до подтверждения; при проблеме сети продолжить просмотр уже сохранённых позиций.

## 3. Требования к системе

### Функциональные требования

Приложение должно выводить товары с изображением, названием, категорией, ценой, описанием и ожидаемой датой; поддерживать поиск по названию; фильтрацию по категории; сортировку по дате поступления, названию и цене; показывать сведения о выбранном товаре; обновлять каталог через публичный HTTP API; предотвращать дубли при повторной синхронизации; сохранять товар и заказ в SQLite; проверять доступность и количество при создании заказа; копировать текущую цену в заказ; показывать список заказов и их статусы; разрешать отмену только заказа в состоянии ожидания подтверждения; сообщать пользователю результат операции и об ошибках сети или базы.

### Нефункциональные требования

Интерфейс должен оставаться настольным и масштабироваться при изменении размеров окна. Повторяющиеся элементы каталога должны иметь одинаковые отступы и визуальную структуру. Сетевые и файловые операции должны быть асинхронными. Источник данных должен подменяться без переписывания бизнес-сервиса. Внешний сервис не должен быть необходим для чтения уже сохранённого каталога. Сборка и тесты должны запускаться через .NET SDK.

### Ограничения

Это демонстрационное приложение для одного локального пользователя. В нём нет авторизации, оплаты, уведомлений поставщика и межустройственной синхронизации. Значение остатка API используется только для локальной проверки; оно не резервирует товар на сервере. Следовательно, такой прототип не следует использовать как коммерческую систему заказов без отдельного серверного компонента и согласования с поставщиком.

## 4. Проектирование приложения

### Архитектура

Используется разделение MVVM. Avalonia View отображает состояние, ViewModel преобразует пользовательские действия в вызовы сервисов и предоставляет свойства интерфейсу, а сервисы содержат сценарии каталога и заказов. `IProductProvider` отделяет DummyJSON от бизнес-логики. `StoreDbContext` выполняет хранение через EF Core. Microsoft .NET Host создаёт контейнер зависимостей и типизированный `HttpClient`.

Последовательность оформления:

1. Пользователь выбирает товар и количество.
2. ViewModel передаёт ID и число сервису магазина.
3. Сервис проверяет положительное количество, товар, доступность и оставшийся демонстрационный запас с учётом уже оформленных незакрытых заказов.
4. В транзакции создаётся запись с текущей ценой и статусом `AwaitingConfirmation`.
5. Интерфейс перечитывает каталог и историю и показывает уведомление.

Последовательность синхронизации:

1. Провайдер получает JSON по HTTPS и десериализует только используемые поля DTO.
2. Провайдер проверяет критические значения и преобразует ID в строку внешнего ключа.
3. Сервис выбирает существующие позиции с совпадающими внешними ID.
4. Совпавшие товары обновляются; новые добавляются; отсутствующие в ответе не удаляются.
5. EF сохраняет изменения. Уникальный индекс внешнего ID защищает от дублирования.

### Модель данных

Сущность `Product` содержит внутренний ключ, уникальный `ExternalId`, название, описание, категорию, цену, URL изображения, локальную дату ожидаемого поступления, демонстрационное наличие и даты создания/обновления. Внешний ключ остаётся строкой, что не связывает схему приложения с конкретным форматом API.

Сущность `PreOrder` содержит ID, внешний ключ на товар, количество, цену единицы на момент заказа, дату создания и статус. Между `Product` и `PreOrder` задана связь один-ко-многим. Для удаления товара из каталога настроено ограничение `Restrict`, так что запись с историей заказов не исчезает каскадно. Количество дополнительно ограничено проверочным выражением `Quantity > 0`. Стоимость хранится в SQLite как decimal с заданной точностью.

Допустимые статусы: `AwaitingConfirmation` («Ожидает подтверждения»), `Confirmed` («Подтверждён»), `Cancelled` («Отменён»), `Fulfilled` («Выполнен»). В интерфейсе прототипа создаётся только первый статус, и отмена доступна только из него. Другие состояния определены для полноты предметной модели, но внешней имитации подтверждения или исполнения система не заявляет.

### Выбор технологий

C# выбран как основной язык реализации. .NET 10 использован как актуальный LTS-релиз на дату проектирования; Avalonia 12 поддерживает .NET 8 и новее и рекомендует .NET 10 [2] [3]. Avalonia обеспечивает XAML и нативную настольную оболочку на поддерживаемых настольных системах. CommunityToolkit.Mvvm формирует уведомляемые свойства и команды. EF Core SQLite предоставляет миграции и проверяемое хранение без отдельного сервера. `HttpClient` вызывается асинхронно с таймаутом. Microsoft.Extensions.Hosting используется для DI и жизненного цикла зависимостей.

## 5. Реализация

Структура решения состоит из `PreOrderStore` и `PreOrderStore.Tests`. В основном проекте каталог `Domain` содержит модели; `Data` — контекст и EF-миграции; `Infrastructure` — DTO и сетевой провайдер; `Services` — синхронизацию и сервис сценариев; `ViewModels` — состояние экрана и команды; `Views` — XAML и загрузчик удалённых изображений. Тестовый проект запускает сервисы на отдельной SQLite in-memory базе, чтобы проверять реальные ограничения SQL, а не только подменённый объект хранилища.

База находится в локальной пользовательской папке приложения. При запуске выполняется миграция схемы. `HttpClient` использует базовый адрес DummyJSON и ограничение времени ожидания. При ошибке HTTP, таймауте или некорректном ответе пользователь получает понятный текст. Если в базе уже есть каталог, ошибка сети не мешает его просматривать.

### Пользовательский интерфейс

Главное окно имеет боковую навигацию между каталогом и предзаказами. Каталог размещает поле поиска, выбор категории, сортировку, карточки и панель подробностей. Для изображений применяется равномерный контейнер и асинхронное получение. Экран заказов показывает позицию, дату, статус, количество и сумму, вычисленную по цене-снимку.

Дизайн использует нейтральные поверхности и один приглушённый зелёный акцент для главного действия. Расстояния и выравнивание повторяются между элементами; оформление не зависит от градиентов, декоративных значков или неподкреплённых рекламных сообщений. Был проверен навык `heydamir/unslop`; он явно описывает веб-технологии и не заявляет официальную проверку Avalonia. Его правила использованы только как ручной UX-чек-лист для XAML, с сохранением атрибуции Damir Sokolovsky и CC BY 4.0 [4].

### Тестовые сценарии

| № | Сценарий | Ожидаемый результат |

| 6 | Повторно отменить заказ | Операция отклонена |
| 7 | Дважды синхронизировать набор с повторяющимся внешним ID | Количество товаров не увеличивается за счёт дублей |
| 8 | Обновить товар, на который есть заказ | Карточка обновляется, история и прежняя цена заказа сохраняются |

Во время разработки `dotnet test PreOrderStore.sln` завершился успешно: пройдено 7 тестовых случаев, ошибок нет. `dotnet build PreOrderStore.sln` также завершился успешно. Запрос к DummyJSON проверен отдельно. Эти результаты относятся к моменту разработки; на другом компьютере рекомендуется повторить команды из README.

### Ограничения проведённой проверки

Проверка публичного API подтвердила доступность и формат ответа только в конкретный момент. Из-за природы демонстрационного API она не проверяет фактический коммерческий резерв товара. Визуальный рендеринг и интерактивные сценарии графического окна необходимо отдельно подтвердить на целевой ОС с установленными библиотеками Avalonia. Для учебной защиты полезно показать запуск и оформить один заказ в окне, а также проверить запись в локальной базе после перезапуска.

## 7. Руководство пользователя

Установите .NET 10 SDK и выполните команды из корня репозитория: сначала `dotnet restore PreOrderStore.sln`, затем `dotnet run --project PreOrderStore/PreOrderStore.csproj`. При первом запуске программа создаёт локальную БД и загружает каталог из сети. Если сеть недоступна, нажмите «Обновить каталог» после восстановления соединения.

Введите часть названия в поле поиска. При необходимости выберите категорию и критерий сортировки. Нажмите «Подробнее» на карточке, проверьте цену, ожидаемую дату и наличие, задайте количество и нажмите «Оформить предзаказ». Откройте вкладку «Предзаказы», чтобы увидеть сохранённый заказ. Пока он ожидает подтверждения, его можно отменить. Повторный запуск сохраняет историю в SQLite.

## 8. Материалы к защите

### Демонстрационный план

1. Показать структуру решения и объяснить разделение на UI, бизнес-сервисы, сетевой клиент и SQLite.
2. Запустить приложение и обновить каталог.
3. Найти позицию, выбрать фильтр и изменить сортировку.
4. Открыть подробности товара и оформить предзаказ.
5. Показать состояние «Ожидает подтверждения», цену-снимок и сумму в списке заказов.
6. Отменить заказ и показать, что состояние изменилось.
7. Перезапустить приложение и показать сохранённый результат.
8. Запустить `dotnet test PreOrderStore.sln` и объяснить тесты бизнес-ограничений.

### Возможные вопросы

**Почему цена копируется в заказ?** Каталог может обновиться. Заказ должен сохранять цену, которую система зафиксировала при его оформлении, а не динамически вычислять прошлую стоимость из текущего каталога.

**Как предотвращаются дубли?** Внешний ID хранится в уникальном индексе. Сервис синхронизации обновляет найденную запись или добавляет новую.

**Почему отсутствующие в API товары не удаляются?** Предзаказы ссылаются на товар. Автоматическое удаление может разрушить историю. В прототипе карточки сохраняются, а реальные бизнес-правила архивации были бы отдельным требованием.

**Поддерживает ли DummyJSON предзаказы?** Нет. Это источник демонстрационных карточек. Заказы и их статусы принадлежат локальному приложению; метод API не используется для создания заказа.

**Как обрабатывается отсутствие интернета?** Ошибка показывается в интерфейсе. Сохранённый каталог остаётся доступен в локальной базе; первоначальный пустой каталог требует соединения для загрузки.

**Почему приложение не содержит авторизацию?** В рамках демонстрации проект локальный и однопользовательский. Авторизация без реального сервера идентификации и нескольких пользователей добавила бы сложность без практической необходимости.

**Как можно развивать систему?** Заменить провайдер на реальный магазинский API, хранить заказы на сервере, добавить учёт пользователей, серверную проверку и резервирование остатков, журнал синхронизации, календарь реальных поставок и интеграционные/UI-тесты на целевых ОС.

## 9. Заключение

В ходе работы спроектирована и реализована основа настольного магазина предзаказов с каталогом из внешнего тестового API, локальным хранением товаров и заказов, обработкой статусов и фиксацией цены на момент оформления. Слои приложения разделены, внешний источник изолирован интерфейсом, повторная синхронизация использует внешний ключ и не разрушает историю заказов.

Работоспособность проверена сборкой .NET и интеграционными тестами на SQLite in-memory; прошли 8 тестовых случаев. Публичный источник был проверен на живом запросе. Приложение остаётся учебной демонстрацией: оно не выполняет реальное резервирование, оплату или подтверждение поставщика. Для коммерческого применения необходимы серверная сторона, согласованные интеграции и методические/предметные требования заказчика.
